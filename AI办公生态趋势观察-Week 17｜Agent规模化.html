Agent 越来越多，
企业如何管得住？

企业治理 · 腾讯产品布局 · 沙箱基础设施

本周行业洞察
AI INSIGHTS · 2026-W45 · 资料截至 2026-11-05
本周关注一个问题：当多个部门都在创建和引入 Agent，企业如何把它们变成可管理、可验收的执行资产。这份汇报先看管理问题，再看腾讯产品布局，最后看沙箱市场与试点计划。范围截至十一月五日，不把历史功能写成当周新闻。

01 / EXECUTIVE TAKEAWAYS

本周结论：先补控制闭环，再扩张数量

01

统一管理

登记负责人、身份和版本；把退出机制纳入上线条件。

02

分层建设

构建、门户、执行与模型各有职责，产品组合需要验证衔接。

03

按任务验收

用完成率、控制效果和成功任务总成本，衡量项目价值。

决策建议：批准一个低风险场景试点，暂不以 Agent 数量作为扩张目标。
S24 · S25 · S07 · S12
这三点是本次研究的分析判断。已有官方产品支持目录、身份、执行和观测等分工，但是否适用于企业现状需要试点。建议先选业务任务，再选平台；评价依据是结果与控制能力。

03 / ENTERPRISE CONTROL STACK

七层底座，把“怎么管”变成清单

注册目录有哪些 Agent，谁负责？ID、负责人、用途、风险、版本、运行地址
身份与权限代表谁，能访问什么？工作负载身份、委托、最小权限、撤权
工具网关能做哪些操作？工具准入、鉴权、参数、限流、敏感操作授权
运行环境在哪里跑，如何停止？隔离、调度、超时、取消、故障恢复
状态与记忆中断怎么续，信息留多久？检查点、隔离、保留期限、删除
观测与评测为什么出错，任务完成了吗？链路、版本、评测、业务结果
预算与生命周期花多少，何时升级或停用？预算、发布门槛、回退、退役及凭证回收
统一控制要求；保留业务团队选择不同框架的空间。
S24 · S25 · S26—S28
七层是项目管理用的分析框架，不是采购清单。盘点、身份、工具出口和执行环境需要衔接；观测与评测提供运行证据；预算和退役负责约束持续成本与权限。

04 / RESPONSIBILITY BOUNDARIES

三个平面，避免把门户当成全部治理

01

构建与管理

谁能创建、修改、发布？
ADP / AgentOps

02

使用与分发

员工能找到、能用哪些？
AgentPortal / 业务入口

03

运行与控制

任务在哪里跑，能访问什么？
Runtime / 身份 / 网关

关键链路：用户 → Agent → 工具 → 数据与业务动作。每一跳都要明确授权。
S02 · S05 · S07 · S35
这是逻辑职责划分。门户使用权限并不自动成为业务系统的数据授权。接入平台时，应该把用户身份、Agent 身份、工具凭证和业务数据权限画成一条可验证的链路。

07 / GOVERNANCE CHECKPOINTS

腾讯治理：看清已支持与待验证

官方已说明

组织、发布与使用

  • 企业—空间—应用管理分层
  • 应用和 Skill 发布审批
  • Portal 按用户 / 部门分配使用范围

仍需项目验证

跨产品与业务控制

  • 高风险动作是否逐次授权
  • 外部 Agent 能否强制受控

官方文档明确：AgentPortal 与 ADP 账号、权限和企业管理体系独立。
S01 · S02 · S05 · S06
已支持的管理功能值得研究，但不能过度推断。审批中心覆盖的是发布；门户管理的是使用范围。独立账号体系意味着身份映射、组织变更与撤权传播要单独验收。

10 / TECHNOLOGY VS. PRODUCT

隔离技术与成品平台，分两层比较

底层组件

如何形成执行边界

  • Firecracker：microVM
  • gVisor：应用与宿主内核间隔离层
  • Kata：容器 / Pod 在轻量 VM 中执行
平台能力

如何让企业持续使用

  • 环境创建、暂停、恢复和资源配额
  • 镜像、网络、凭证、身份与日志
  • SDK、控制台、计费和运维支持
E2B 与 Firecracker 并非同层竞品；普通容器也不能自动等同于完整 Agent 沙箱平台。
S12 · S21—S23
底层技术说明隔离机制，平台能力说明是否好接、好管和可运营。企业通常需要两张表：一张评估技术边界，一张评估产品与运维。不要拿组件直接对照平台的全部功能。

11 / USE CASE TO VALUE

业务价值：从任务到可验收结果

任务依赖能力可验收结果
企业知识服务解析、权限检索、答案证据回答有来源，越权查询受阻
经营分析报告代码、文件、状态、产物计算可复算，报告可追踪
研发任务仓库授权、命令隔离、测试变更经过检查并有责任人
询价与报价实时数据、规则、人工确认异常转人工，不重复处理
传媒内容多模型、工作流、素材审核产物可定位，审核记录完整
案例帮助理解路径；本企业收益仍需真实样本验证。
S04 · S30 · S33 · S34
找钢和传媒等行业方案说明了智能体如何进入流程。项目验收要回到业务结果：计算是否正确、是否经过必要审批、是否重复执行、产物是否可定位。厂商案例不能直接成为企业收益承诺。

12 / RISKS & ACCEPTANCE

五个误判，转成五组验收测试

不要混淆重点验证
统一入口 ≠ 统一授权逐层验证用户→Agent→工具→业务数据
发布审批 ≠ 动作审批将业务动作控制单独设计并测试
环境恢复 ≠ 业务回滚验证幂等、去重、补偿和外部状态
MCP / A2A ≠ 企业治理补充身份、策略执行和目录机制
产品组合 ≠ 全域纳管确认发现范围、强制接入和撤权效果
优先测试失败路径：撤权、取消、超时、重试、重复操作与预算耗尽。
分析建议 / 参考 S02 · S06 · S26 · S27
测试不只看成功演示。尤其要让任务在执行到一半时被取消，或者工具返回失败后触发重试，观察外部动作有没有重复发生。这里列的是建议测试场景，不代表产品已经存在这些问题。

P1 · 复盘、明确边界，决定扩展或停止

项目经理 + 决策人

形成试点验收报告与下一阶段决策
建议排期：D0 为立项日。先低风险任务，业务写入另设授权与回退方案。
RECOMMENDATION / 拟议计划
这是一份建议计划，责任角色不是已指派人员。第一周定范围，第二周测控制，第三周测质量和成本，第四周做是否扩展的决策。每一步都需要一个可评审的交付物。

14 / PROJECT SCORECARD

核心指标：成功任务，而非调用数量

建议成本指标单次成功任务总成本
模型 + 沙箱 + 存储 + 网络 + 观测 + 人工复核
÷ 通过业务验收的任务数
01

质量

任务完成率、答案 / 产物正确性。

02

控制

撤权、取消、越权阻断和重复动作。

03

效率

延迟分布、人工接管率、总成本。

RECOMMENDATION / 指标口径
先固定任务集和验收标准再比较成本，否则便宜方案可能只是失败得更多。总成本需要包含人工复核和执行资源。这里不设通用行业阈值，由业务容错和预算决定。
